# 파이썬 · Git 기초 퀴즈

터미널에서 동작하는 4지선다 퀴즈 게임입니다. Python 기본 문법, 클래스, JSON 파일 입출력과 Git을 연습합니다.

## 주제와 선정 이유

파이썬과 Git 기초를 주제로 선정했습니다. 개발 입문 미션에서 배우는 개념을 퀴즈로 복습하기에 적합하기 때문입니다. 기본 문제는 8개이며, 프로그램에서 새 문제를 추가할 수 있습니다.

| 기본 문제 분류 | 문제 내용 | 개수 |
| --- | --- | --- |
| Python 기본 문법 | 출력, 정수 자료형, 조건문, 함수 정의 | 4 |
| 클래스·데이터 저장 | `__init__`, JSON과 dict | 2 |
| Git 기초 | commit, clone | 2 |

기본 문제 8개는 모두 입문 개념 확인용입니다. 실행 예시의 9번째 문제는 퀴즈 추가 기능으로 등록한 문제이며, 기본 문제 수와 구분합니다.

## 실행 방법

Python 3.10 이상이 필요합니다. 외부 패키지 설치는 필요 없습니다.

```powershell
cd codyssey-quiz
python --version
python main.py
```

`python`이 인식되지 않으면 Python을 설치하고 PATH에 등록하거나 설치된 Python 실행 파일의 전체 경로를 사용하세요. 작업 폴더가 달라도 데이터는 main.py 옆에 저장됩니다.

## 기능

1. 퀴즈 풀기: 전체 문제 출제, 정답/오답 안내, 결과와 최고 점수 갱신
2. 퀴즈 추가: 문제, 선택지 4개, 정답 번호 입력 및 즉시 저장
3. 퀴즈 목록: 등록한 문제 확인
4. 점수 확인: 완료한 게임의 최고 점수 확인
5. 종료: 데이터 저장 후 종료

숫자 입력은 앞뒤 공백을 제거하고 빈 입력, 문자와 범위 밖 숫자를 거절합니다. Ctrl+C와 EOF는 저장 후 종료합니다. 중단된 게임의 점수와 입력이 끝나지 않은 새 문제는 반영하지 않습니다.

## 데이터 파일

프로젝트 루트의 `state.json`을 UTF-8로 저장합니다. 사용자 데이터와 백업 파일은 Git에서 제외합니다.

```json
{
  "quizzes": [
    {"question": "정수를 나타내는 자료형은?", "choices": ["str", "bool", "int", "list"], "answer": 3}
  ],
  "best_score": null
}
```

- `quizzes`: 문제 객체 목록. 선택지는 4개, 정답 번호는 1~4입니다.
- `best_score`: 최고 점수 0~100 정수, 미플레이 상태는 `null`입니다.
- 점수는 `round(정답 수 / 전체 문제 수 * 100)`으로 계산합니다.
- 파일이 없으면 기본 데이터로 시작합니다. 손상된 파일은 기본 데이터로 복구하며 다음 저장 전에 `.bak` 파일로 원본을 보관합니다.
- 임시 파일에 쓴 뒤 교체하여 저장 중 원본 손상 가능성을 줄입니다. 읽기·쓰기 오류는 안내 메시지로 표시합니다.

## 커밋 단위와 메시지 규칙 (평가 #12)

한 커밋에는 한 가지 설명 가능한 변경을 담습니다. 예를 들어 문제 모델 작성, 기본 문제 등록, 입력 검증, 플레이 기능, 문서 보완을 각각 나눕니다. 단순히 커밋 수를 늘리기 위한 빈 커밋이나 동일 파일의 의미 없는 반복 수정은 하지 않습니다. 여러 파일을 바꿔도 하나의 기능을 완성하는 변경이면 함께 커밋할 수 있습니다.

메시지 형식은 `타입: 무엇을 변경했는지`입니다. 현재 기록은 범위(scope)를 별도 괄호로 적지 않고, 본문에 `Quiz`, 입력 검증, README 등 수정 대상을 적습니다. 제목은 한 줄로 작성하고, 필요하면 본문에 변경 이유와 검증 방법을 덧붙입니다.

| 접두사 | 사용 범위 | 실제 기록 예 |
| --- | --- | --- |
| `Feat:` | 새 기능·데이터 | `Feat: 퀴즈 출제와 결과 집계 및 최고 점수 갱신` |
| `Fix:` | 기존 동작의 오류 수정 | 사용 예: `Fix: 점수 계산 오류 수정` (현재 이력에 이 제목의 커밋이 있다는 뜻은 아님) |
| `Refactor:` | 외부 동작을 유지하는 구조 개선 | 사용 예: `Refactor: QuizGame 책임 분리` (향후 적용 예시) |
| `Test:` | 테스트와 실제 검증 결과 | `Test: 저장 복원과 입력 오류 및 중단 상황 11개 검증` |
| `Docs:` | README·설명·실행 증거 | `Docs: GitHub 업로드와 실제 clone pull 실습 완료 기록` |
| `Chore:` | 프로젝트·실행 환경 설정 | `Chore: 퀴즈 프로젝트와 사용자 데이터 제외 규칙 설정` |
| `Merge:` | 기능 브랜치를 통합하는 병합 커밋 | `Merge: 퀴즈 플레이 기능 병합` |

실제 작성자는 `Codex <codex@localhost>`이며 AI 도움으로 구현한 기록을 유지했습니다. 작성자나 작성 시각을 학습자의 직접 작업처럼 바꿔 기록하지 않았습니다. 실제 작성·커밋 시각과 커밋 개수는 [Git 상세 기록](docs/git-history-detailed.txt), 간단한 그래프는 [git-log.txt](docs/git-log.txt)에서 확인할 수 있습니다. 문서 보완 전 기준 main에서 도달 가능한 커밋은 17개이며, 최신 개수는 `git rev-list --count HEAD`로 확인합니다.

## 브랜치 전략과 병합 정책 (평가 #6, #16)

| 브랜치 | 역할 | 실제 사용 내역 |
| --- | --- | --- |
| `main` | 통합한 프로젝트를 보관하고 제출하는 기준 브랜치 | 코드, 문서, 검증 자료를 통합하여 GitHub에 push |
| `feature/quiz-play` | 퀴즈 출제·정답 판정 흐름·점수 갱신을 분리해서 추가하는 기능 브랜치 | `be48bba`에서 분기, `d71c12f`로 플레이 기능 추가, `d46e142`로 main에 병합 |

브랜치를 나누는 이유는 개발 중인 플레이 기능을 main과 분리하여 변경 내용을 검토하고, 다른 기능과 섞이지 않게 실험하기 위해서입니다. 브랜치는 파일 사본 폴더가 아니라 커밋을 가리키는 별도의 작업 흐름입니다. 다른 작업자는 main을 기준으로 작업하면서도 기능 브랜치의 변경을 따로 살펴볼 수 있습니다.

병합은 기능 브랜치에서 검토한 변경과 이력을 main의 흐름에 통합하는 작업입니다. 실제 병합은 `--no-ff`로 수행하여 부모가 둘인 병합 커밋을 남겼습니다. `d46e142`의 부모는 main 쪽 `be48bba`와 기능 쪽 `d71c12f`입니다. 기능이 어느 흐름에서 추가됐는지 그래프로 확인할 수 있도록 기능 브랜치도 원격에 보관했습니다.

실제 작업 순서는 `checkout -b feature/quiz-play` → 기능 추가·commit → `checkout main` → `merge --no-ff feature/quiz-play` → 원격 push입니다. 과거 이력에서 실행 시작점과 자동 테스트는 병합 이후에 추가됐으므로, 병합 전에 전체 자동 테스트를 실행했다고 주장하지 않습니다. 현재 버전은 통합 후 테스트 11개를 통과했습니다. 향후에는 기능 브랜치에서 실행 검증을 마친 뒤 병합하며, 충돌이 생기면 충돌 파일을 검토·수정하고 검증 후 병합을 완료합니다. 원격 이력은 강제로 덮어쓰지 않고, 동기화는 `pull --ff-only`를 우선 사용합니다.

## 클래스를 사용한 이유와 함수 기반 대안 (평가 #8, #9, #13)

함수만으로도 같은 게임을 만들 수 있습니다. 예를 들어 문제를 dict로 저장하고 `display_quiz(quiz_dict)`, `is_correct(quiz_dict, answer)`, `play(quizzes, best_score)`처럼 필요한 데이터를 인자로 전달하는 방식입니다. 문제 수와 기능이 작으면 이 방법도 간결합니다.

이 프로젝트에서는 문제의 데이터와 검증·동작을 함께 다루기 위해 `Quiz`를 선택했습니다. 예를 들어 `Quiz(question, choices, answer)`를 생성할 때 선택지 4개와 정답 1~4를 검증하고, 이후에는 같은 객체의 `display()`와 `is_correct()`를 사용합니다. 함수와 dict만 사용할 경우 문제 생성 경로마다 동일한 검증 함수를 호출하고 키 이름을 일관되게 관리해야 합니다. 클래스는 그 규칙을 한 생성 지점에 모으는 데 도움이 됩니다. 다만 클래스만 쓴다고 모든 수정이 자동 검증되는 것은 아닙니다. 생성 후 속성을 직접 바꾸는 코드는 검증을 우회할 수 있으므로 피해야 합니다.

`QuizGame`은 서로 연관된 퀴즈 목록, 최고 점수, 저장 경로를 인스턴스 상태로 묶습니다. 함수 기반 대안은 이 상태를 각 함수의 인자·반환값으로 주고받거나 별도 상태 dict로 관리해야 합니다. 예를 들어 문제 추가 시 목록과 저장 경로를 전달하고, 플레이 후 갱신한 점수를 호출자에게 돌려줘야 합니다. `QuizGame`에서는 `add_quiz()`와 `play()`가 같은 인스턴스 상태를 갱신하고 저장합니다. 반대로 단순 문자열·숫자 입력 검증은 인스턴스 상태가 필요 없어 `inputs.py`의 함수로 남겼습니다. 상속 구조는 필요하지 않아 도입하지 않았습니다.

| 책임 | 담당 파일·메서드 | 경계 사례 |
| --- | --- | --- |
| 문제 한 개의 유효성 | `quiz.py` / `Quiz.__post_init__()` | 빈 문제·선택지 수·정답 범위 검증; 메뉴 번호는 검증하지 않음 |
| 문제 표시·정답 비교 | `Quiz.display()`, `Quiz.is_correct()` | 문제 내용과 정답 일치만 담당; 전체 게임 점수 계산은 하지 않음 |
| 저장 가능한 문제 자료 변환 | `Quiz.to_dict()`, `Quiz.from_dict()` | 객체↔dict 변환만 수행; 파일 열기·백업은 하지 않음 |
| 메뉴·문제 순회·점수 집계 | `game.py` / `QuizGame.run()`, `show_menu()`, `play()` | 정답 개수 집계와 최고 점수 비교는 여러 문제를 관리하는 Game의 책임 |
| 추가·목록·점수 조회 | `QuizGame.add_quiz()`, `list_quizzes()`, `show_score()` | 완성된 문제만 목록에 추가하며, 미플레이 상태는 `None`으로 구분 |
| 파일 읽기·쓰기·백업 | `QuizGame.load_state()`, `save_state()` | 저장 경로와 전체 문제·점수를 아는 Game에서 수행 |
| 공통 사용자 입력 | `inputs.py` / `read_number()`, `read_text()` | `read_number(..., 1, 5)`는 메뉴, `read_number(..., 1, 4)`는 정답 선택에 재사용 |
| 기본 문제 생성 | `defaults.py` / `default_quizzes()` | 처음 실행하거나 파일 복구 시 사용할 새 Quiz 인스턴스들을 반환 |

입력 검증과 데이터 IO를 나눈 기준은 오류의 원인과 재시도 위치입니다. `abc`를 정답 번호로 입력하면 `read_number()`가 안내하고 같은 입력을 다시 받습니다. 디스크 저장 실패는 사용자 입력을 바꿔도 해결되지 않으므로 `save_state()`가 실패를 반환하고 폴더 권한·공간 확인을 안내합니다. 파일에서 읽은 데이터는 사용자 입력 검증 함수를 거치지 않기 때문에, `load_state()`와 `Quiz.from_dict()`에서도 별도로 구조·값을 검증합니다.

## JSON 선택 이유, 성능·메모리·동시성 한계 (평가 #3, #14, #18)

JSON은 Python 표준 라이브러리 `json`으로 처리할 수 있고, list/dict/str/int/null 구조로 문제 목록과 점수를 표현하기 쉽습니다. 외부 DB 설치가 필요 없고 사람이 파일을 읽을 수 있어 소규모 단일 사용자 학습용 게임에 적합합니다. UTF-8과 `ensure_ascii=False`로 한글을 읽기 쉽게 저장하며, `indent=2`는 검토 편의를 위한 들여쓰기입니다.

장점은 구조가 단순하고 다른 언어에서도 읽기 쉽다는 점입니다. 한계는 DB처럼 인덱스·부분 갱신·트랜잭션·동시성 제어를 제공하지 않는다는 점입니다. `json.load()`는 파일 전체를 메모리로 읽어 해석하고, 문제 dict 목록을 Quiz 객체 목록으로 변환하는 동안 원본 데이터와 객체들이 동시에 존재합니다. 문제 수를 n, 전체 파일 크기를 B라고 하면 읽기·전체 직렬화 작업량은 대략 O(B), 보관 메모리는 전체 데이터 크기에 비례합니다. 파일이 커지면 시작 시간·저장 시간·메모리 사용량이 모두 증가합니다. 손상 원본의 백업도 `read_bytes()`를 사용하므로 파일 크기에 비례하는 추가 메모리가 필요합니다.

문제 하나를 추가해도 `save_state()`는 전체 문제 목록과 최고 점수를 다시 씁니다. 검색용 인덱스와 페이지 단위 읽기가 없어 수십만 개 이상의 큰 문제 모음에 적합한 설계는 아닙니다. `quizzes`는 메모리에 계속 보관되므로 필요한 문제만 읽는 지연 로딩도 구현되어 있지 않습니다. 구체적인 허용 문제 수는 문제 문자열 길이와 장치에 따라 달라지므로 측정하지 않은 성능 수치를 보장하지 않습니다.

동시 실행도 지원하지 않습니다. 두 프로그램이 같은 파일을 읽고 각각 수정하면 마지막 저장이 다른 실행의 변경을 덮어쓸 수 있습니다. 임시 파일 이름 `state.json.tmp`도 공유하므로 동시 쓰기가 서로 간섭할 수 있습니다. `os.replace()`는 완성한 파일로 교체하는 방식이지 파일 잠금이나 사용자별 트랜잭션이 아닙니다. `fsync()`도 호출하지 않으므로 전원 장애까지 포함한 저장 내구성을 보장하지 않습니다. 현재 사용 범위는 같은 저장 파일을 사용하는 프로그램 1개입니다. 대용량·다중 사용자로 확장할 때는 SQLite 등의 DB, 트랜잭션·잠금, 부분 조회·갱신, 스키마 마이그레이션을 설계해야 합니다. 이는 향후 개선 방향이며 현재 구현 기능은 아닙니다.

## 저장·복구·중단 시 처리 흐름 (평가 #10, #11, #15, #19)

저장 시점 요약: 새 퀴즈 입력을 완성한 직후, 한 게임의 모든 문제를 완료한 뒤, 정상 종료 또는 Ctrl+C/EOF로 종료할 때 저장합니다. 손상·읽기 오류가 발생한 기존 파일은 다음 저장 전에 원본 백업을 시도합니다.

```text
시작 → 기본 퀴즈 8개와 최고 점수 None 준비
     → state.json을 UTF-8로 읽기 → JSON 해석 → 구조·문제·점수 검증
         ├─ 성공: 읽은 문제 목록·최고 점수 적용
         ├─ 파일 없음: 기본 데이터로 시작
         └─ 손상/읽기 오류: 안내 → 기본 데이터 유지 → 백업 필요 표시

저장 → 백업 필요하며 원본이 있으면 .bak으로 보관
       (기존 백업이 있으면 .bak1, .bak2 ... 사용)
     → Quiz.to_dict()로 문제 목록 변환
     → state.json.tmp에 UTF-8 JSON 기록 후 파일 닫기
     → os.replace()로 state.json 교체
     → 성공 반환 / 오류 발생 시 안내하고 실패 반환
```

읽은 데이터는 모든 검증이 끝난 후에만 인스턴스에 적용합니다. 따라서 중간 문제의 구조가 잘못됐을 때 앞부분만 섞여 적용되지 않습니다. 원본 백업이 실패하면 해당 저장은 실패 처리하고 임시 저장·원본 교체를 진행하지 않습니다. 원본이 없으면 백업할 파일이 없어 기본 데이터를 바로 저장합니다.

| 상황 | 프로그램 동작 | 권장 대처·재시도 |
| --- | --- | --- |
| `abc`, 빈 입력, 메뉴 `9`, 정답 `0` | 허용 범위 안내 후 같은 질문으로 복귀 | 1~5 메뉴 번호 또는 1~4 정답 번호 재입력 |
| 파일 없음 | 기본 문제·미플레이 점수로 시작 | 다음 정상 저장에서 파일 생성 |
| 잘못된 JSON·스키마·UTF-8 | 안내 후 기본 데이터 사용, 다음 저장 전 원본 백업 | `.bak` 원본을 확인하고 유효한 파일로 복원하거나 기본 데이터 사용 |
| 읽기/백업 권한 오류 | 기본 데이터로 시작하더라도 원본 백업 실패 시 저장 중단 | 프로그램 폴더·파일의 권한을 확인한 뒤 다시 실행; 기존 파일을 임의 삭제하지 않음 |
| 쓰기 실패·공간 부족 | 실패 메시지, 현재 실행의 메모리 데이터 유지 | 종료 전 권한·공간 문제를 해결하면 종료 시 저장을 다시 시도함; 실패가 지속되면 변경 유실 가능 |
| Ctrl+C 또는 EOF | 안내 후 `finally`에서 현재 상태 저장 시도 | 입력 중이던 새 퀴즈와 끝나지 않은 게임 점수는 미반영; 기존 문제와 이전 최고 점수 보존 |

자동으로 일정 시간마다 재시도하거나 별도의 오류 로그를 저장하는 기능은 없습니다. 추가·플레이 시 저장 실패 후에는 실행 상태를 유지하고 종료 시 다시 저장합니다. 이미 종료한 뒤에는 메모리에만 있던 내용을 복구할 수 없으므로 저장 실패 메시지를 확인해야 합니다.

예를 들어 퀴즈 추가 중 문제와 선택지 2개만 입력하고 Ctrl+C를 누르면, `append()` 이전이므로 그 문제는 등록되지 않습니다. 플레이 중 일부 문제만 푼 뒤 중단하면 결과 집계 이전이므로 이전 최고 점수를 유지합니다. 완료한 게임의 0점은 정수 `0`으로 저장하여 아직 플레이하지 않은 `null`과 구분합니다.

손상 복구·초기화 절차는 다음과 같습니다. 별도의 초기화 메뉴는 구현하지 않았습니다.

1. 프로그램의 오류 안내를 확인합니다. 실행을 계속한 후 저장에 성공하면 기본 데이터가 state.json에 기록되고 손상 원본은 `.bak` 계열에 보관됩니다.
2. 사용자 문제를 복구하려면 프로그램을 모두 종료하고 원본·백업을 별도로 보관합니다. 백업이 손상 JSON 자체일 수 있으므로 `.bak`이라는 이유만으로 유효하다고 가정하지 않습니다.
3. 파일을 UTF-8로 열고 아래 스키마와 비교해 수정한 복사본을 검증한 뒤 `state.json`으로 배치하고 재실행합니다. `python -m json.tool state.json`은 JSON 문법 검사이며, 문제 수·정답 범위 등의 의미 검증은 앱 실행에서도 수행합니다.
4. 기본 데이터로 수동 초기화하려면 종료 상태에서 기존 `state.json`을 고유한 백업 이름으로 옮겨 보관하고 다시 실행합니다. 파일이 없으므로 기본 문제 8개와 미플레이 점수로 시작하며 다음 저장 때 새 파일을 만듭니다.
5. 백업·쓰기 실패가 계속되면 권한과 디스크 공간을 해결하기 전까지 복구 완료로 간주하지 않습니다.

## 입력 실패 사례와 전체 메뉴 실행 예시 (평가 #1, #2)

| 입력 위치 | 입력 예 | 기대 동작 |
| --- | --- | --- |
| 메뉴 | 앞뒤 공백이 있는 ` 3 ` | 공백 제거 후 목록 표시 |
| 메뉴 | `abc`, 빈 Enter, `9` | `1~5 사이의 숫자를 입력하세요.` 후 재입력 |
| 정답 | `abc`, 빈 Enter, `0`, `5` | `1~4 사이의 숫자를 입력하세요.` 후 같은 문제의 정답 재입력 |
| 문제·선택지 | 빈 문자열 또는 공백만 입력 | `빈 내용은 등록할 수 없습니다. 다시 입력하세요.` 후 재입력 |

메뉴 1~5의 전체 흐름, 잘못된 입력, 추가 후 목록, 정답/오답, 최고 점수, 종료·재실행을 연결한 실제 검증 기록은 [session-walkthrough.txt](docs/session-walkthrough.txt)에 있습니다. 재현 도우미 [demo_walkthrough.py](docs/demo_walkthrough.py)는 실제 `QuizGame`을 호출하고 입력값을 화면에 함께 기록합니다. 자동 입력임을 표시하며 별도 임시 폴더를 사용하므로 사용자 state.json을 바꾸지 않습니다.

## 데이터 필드와 확장 시 주의 사항 (평가 #17)

| 필드 | 예 | 현재 의미·검증 |
| --- | --- | --- |
| `quizzes` | `[{...}]` 또는 `[]` | 문제 객체 목록; 빈 목록도 허용하고 플레이·목록에서 안내 |
| `quizzes[].question` | `"정수를 나타내는 자료형은?"` | 비어 있지 않은 문자열 |
| `quizzes[].choices` | `["str", "bool", "int", "list"]` | 비어 있지 않은 문자열 4개 |
| `quizzes[].answer` | `3` | 1부터 시작하는 정수 번호, bool·문자열은 거절 |
| `best_score` | `100`, `0`, `null` | 0~100 정수 또는 미플레이 상태; bool은 거절 |

힌트를 확장한다면 `Quiz.hint` 속성만 추가하는 것으로 끝나지 않습니다. `to_dict()`의 저장 필드와 `from_dict()`의 기본값·검증을 함께 바꾸고, 기존 파일에 hint가 없어도 읽히는 이전 버전 호환성을 정해야 합니다. `schema_version`, 문제 ID, 카테고리·작성일 같은 메타데이터를 추가하는 방법도 있으나 현재 파일에는 이 필드를 저장하지 않습니다. 현재 `from_dict()`는 지정한 3개 필드만 사용하므로 임의로 추가한 필드가 다음 저장에서 유지된다고 가정하면 안 됩니다.
